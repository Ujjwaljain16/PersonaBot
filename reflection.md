# Reflection

This assignment made the GIGO principle feel practical instead of abstract. At the start, it was tempting to think the hardest part would be building the UI or connecting the API. In reality, the quality of the app depended much more on the quality of the persona prompts. When the prompts were too generic, the model answered in a flat, interchangeable voice. Once I added real beliefs, speech patterns, few-shot examples, and hard constraints, the chatbot started sounding noticeably closer to the three people we were trying to represent.

The most useful decision was separating the project into server-side persona prompts and client-safe persona metadata. That kept the system instructions out of the browser bundle and made the code easier to maintain. It also helped the app behave correctly when switching personas, because the conversation could reset cleanly without the wrong prompt leaking into the next chat. The streaming update later improved the experience even more, because the app no longer felt like it was freezing while waiting for the full response.

I also learned that prompt engineering is not just about writing clever text. It is about reducing ambiguity. The few-shot examples mattered because they showed the model what a good answer looks like in context. The constraints mattered because they stopped the model from drifting into generic advice, motivational filler, or mismatched tone. In other words, the prompt became a small specification, not just a description.

There were also real implementation lessons. The first versions of the UI looked fine on desktop but had mobile issues, so I had to tighten the persona switcher, message bubble widths, and composer layout. That reinforced that a good assignment submission needs both good prompt design and a reliable interface. A chatbot that sounds authentic but breaks on mobile still feels unfinished.

If I had more time, I would do a deeper comparison test for each persona using the same question set and document where their voices still overlap. I would also add screenshots to the README and deploy the app publicly so the submission is easier to verify. Overall, this project showed me that strong outputs come from strong inputs, but only if the prompt, backend, and UI are all aligned.

One practical takeaway was that small implementation details can change how polished the project feels. Streaming removed the wait time, the markdown renderer made the replies readable, and the mobile layout fixes made the app usable on a phone instead of only on a laptop. I also learned to verify things instead of assuming them: checking the word count on the reflection, running type-check after every change, and testing the reset behavior after switching personas all caught issues early. That made the work feel less like a demo and more like a complete product.
That process also made me more careful about how I judge model quality, because good prompts only matter if the outputs are tested against real questions, edge cases, and user expectations throughout each iteration.
